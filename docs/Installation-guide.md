# Installation guide: расчёт аппаратных ресурсов

> Расчёт аппаратных требований продакшен-сервера под целевую нагрузку
> **100 пользовательских сессий в день**. Порядок деплоя и команды —
> в [dev_guide.md](dev_guide.md); сервисы и секреты — в
> [vm_services.md](vm_services.md).

## 1. Назначение и целевая нагрузка

Документ отвечает на вопрос «какой сервер нужен»: покомпонентный расчёт
памяти, CPU и диска для текущей архитектуры проекта и обоснование
рекомендованной и минимальной конфигураций.

Целевая нагрузка: **100 сессий диалога в день** (один пользовательский
диалог = одна сессия).

## 2. Архитектура развёртывания

Продакшен — один сервер (Ubuntu 24). Состав по
`deploy/docker-compose.prod.yml`:

| Компонент          | Что делает                                                                                                      |
|--------------------|-----------------------------------------------------------------------------------------------------------------|
| `kinobot`          | Telegram-бот (polling): приём апдейтов, вызовы внешних API, in-memory сессии и кэш поиска                       |
| `kinobot_postgres` | PostgreSQL 15 (alpine): только админ-панель и статистика                                                        |
| ОС + Docker Engine | контейнеризация; сборка образа приложения на самом сервере при каждом деплое; старые образы хранятся для отката |

Веб-интерфейс/админка (`app.py`) сейчас не деплоится (решается
отдельно) — в расчёте не участвуют.

Ключевая особенность: тяжёлые вычисления выполняются вне сервера —
инференс в GigaChat/DeepSeek и данные о фильмах в Kinopoisk API. Сервер
занят сетевым ожиданием, а не вычислениями, поэтому нагрузка на CPU
близка к нулю в рабочем состоянии.

## 3. Модель нагрузки

- 100 сессий в день ≈ 8 сообщений на сессию (диалог с интентами
  initial / info / similar / alternative) ≈ **800 сообщений в день**.
- На сообщение: 1–2 вызова LLM (классификация интента + извлечение
  параметров) и 0–5 запросов Kinopoisk API — весь трафик исходящий,
  к внешним сервисам.
- Распределение по времени неравномерное: ~60% трафика приходится на
  4 вечерних часа → ~15 сессий/час в пике.
- Пиковая одновременность: **не более 2–5 активных сессий**.

Вывод: целевая нагрузка для сервера минимальна; узкие места искать не
в обработчиках запросов, а в фоновых потребителях (ОС, Docker, сборка
образа при деплое).

## 4. Расчёт по компонентам

Аналитические оценки — консервативные верхние границы рабочего
состояния; фактические измерения текущего сервера приведены в разделе 7.

| Компонент                                                                                                | RAM             | CPU                   | Диск                  |
|----------------------------------------------------------------------------------------------------------|-----------------|-----------------------|-----------------------|
| `kinobot` (Python 3.11, python-telegram-bot, aiohttp, SQLAlchemy; in-memory сессии и кэш по `CACHE_TTL`) | 200–400 МБ      | ≈0 (сетевое ожидание) | —                     |
| `kinobot_postgres` (статистика/админка, порт наружу не публикуется)                                      | 150–250 МБ      | ≈0                    | <100 МБ данных за год |
| ОС Ubuntu 24 + Docker Engine                                                                             | 400–600 МБ      | фоновая               | ~5 ГБ                 |
| Образы: `kinobot-ai:<тег>` (3–5 тегов для отката) + базовые (`python:3.11-slim`, `postgres:15-alpine`)   | —               | —                     | ~1,5–2 ГБ             |
| Логи (том `app_logs`)                                                                                    | —               | —                     | ≤0,5 ГБ               |
| **Итого установившееся**                                                                                 | **~1,2–1,5 ГБ** | **<0,2 ядра**         | **~8 ГБ**             |

Контрольная сумма сходится с итоговой конфигурацией из раздела 5:
1,2–1,5 ГБ рабочего потребления + запас на пик сборки и страничный кэш
= 4 ГБ рекомендованной конфигурации (~2× запас).

Пиковая нагрузка на сервер — **не** пользовательский трафик, а сборка
образа при деплое (`pip install`): кратковременно +300–500 МБ и
заметная загрузка CPU на 1–3 минуты. На конфигурациях с малым объёмом
памяти и без swap это главный риск (см. раздел 6).

## 5. Итоговые конфигурации: один сервер или несколько

**Рекомендованная** (запас ~2×, покрывает сборку образа и будущий
деплой веб/админки +200–300 МБ):

| Параметр   | Значение      |
|------------|---------------|
| Серверов   | **1**         |
| ОС         | Ubuntu 24 LTS |
| vCPU       | 2             |
| RAM        | 4 ГБ          |
| Диск       | 25–30 ГБ SSD  |

**Минимально допустимая** (работоспособна под целевой нагрузкой,
без запаса):

| Параметр   | Значение                                                               |
|------------|------------------------------------------------------------------------|
| Серверов   | 1                                                                      |
| ОС         | Ubuntu 24 LTS                                                          |
| vCPU       | 1                                                                      |
| RAM        | 2 ГБ + **обязательно** swap-файл 1 ГБ (компенсирует пик сборки образа) |
| Диск       | 15–20 ГБ SSD                                                           |

**Несколько серверов не нужны**: нагрузка минимальна, требований к
отказоустойчивости нет; разнос бота и БД по разным серверам только
усложнит деплой. Горизонтальное масштабирование бота в текущей
архитектуре дополнительно упирается в in-memory сессии и кэш, поэтому
при росте нагрузки первый шаг — вертикальный апгрейд одного сервера.

## 6. Критерии пересмотра конфигурации

Проверка на сервере: `free -h` (RAM/swap), `top`/`vmstat` (CPU),
`df -h /` (диск), `docker stats --no-stream` (по контейнерам).

| Признак | Действие                                                                                                            |
|---|---------------------------------------------------------------------------------------------------------------------|
| Свободная RAM устойчиво <10–15% или активно используется swap | увеличить RAM до следующего уровня (2 → 4 ГБ)                                                                       |
| Загрузка CPU устойчиво >70% вне моментов деплоя | добавить vCPU                                                                                                       |
| Диск занят >70% | удалить старые образы (`docker image prune`, оставить 3–5 тегов `kinobot-ai`), при повторном росте — увеличить диск |
| Нагрузка существенно выше 100 сессий/день | перейти на рекомендованную конфигурацию, далее вертикальный апгрейд                                                 |
| Деплой веб-интерфейса/админки | пересчитать расчёт (веб добавит ~200–300 МБ и отдельный процесс)                                                    |

Рекомендация для минимальных конфигураций: деплой (сборку образа)
выполнять вне пиковых вечерних часов. После первых недель продакшена
сверить аналитические оценки с фактическим потреблением
(`docker stats`, `free -h`) и при расхождении уточнить данный расчёт.

## 7. Соответствие текущего сервера

Измерено на продакшене (38.180.228.133), 2026-08-31:

| Параметр | Факт | Оценка |
|---|---|---|
| ОС | Ubuntu 24 | соответствует |
| vCPU (`nproc`) | 1 | минимальная конфигурация |
| RAM (`free -h`) | ~957 МБ, доступно ~443 МБ | **ниже минимальных 2 ГБ** |
| Swap | отсутствует | **риск при сборке образа** |
| Диск | 20 ГБ, занято 8,3 ГБ (44%) | достаточно, запас есть |
| Контейнеры | `kinobot` ~69 МБ, `kinobot_postgres` ~34 МБ (в простое) | фактическое потребление заметно ниже аналитических оценок — нагрузка пока минимальна |
| Образы | 3 шт., 729 МБ (в т.ч. 1 тег `kinobot-ai`) | в пределах расчёта |

Вывод: текущий сервер пока справляется, потому что фактическая нагрузка
много ниже целевой, но **не соответствует минимальной конфигурации**
по RAM и не имеет swap. До выхода на целевую нагрузку рекомендуется:
как минимум — создать swap-файл 1 ГБ; оптимально — апгрейд до
рекомендованной конфигурации (2 vCPU / 4 ГБ / 25–30 ГБ).
