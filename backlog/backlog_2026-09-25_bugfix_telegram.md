## Риски и ограничения

1. **Промпты — источник поведения (AGENTS.md):** правка `parameter_extraction_prompt.txt` (B1.3) меняет классификацию ВСЕХ запросов на обоих каналах (бот + веб) без правки кода — обязателен прогон существующих тестов интентов и B5.
2. **Ловушка дубля моделей БД:** любая схема (B7) синхронизируется в `src/models/database.py` И `init_db.py`; B1 намеренно избегает схемы, храня `awaiting_mood` в JSON `last_params`.
3. **In-memory/БД-сессии:** `SessionManager` частично персистентен (`dialogue_sessions`), но рестарт может терять несохранённое — флаг `awaiting_mood` должен переживать сохранение сессии (писать через штатный `save`).
4. **B2 меняет зафиксированное решение B8 (design.md D1/D4):** снятие reply-клавиатуры было сознательным — новое решение (send+delete либо полное удаление) задокументировать в OpenSpec-изменении, чтобы история решений не потерялась.
5. **Нет dry-run Telegram (AGENTS.md):** проверка бота — только импорт-чек и unit-тесты с моками PTB; реальный polling в тестах не запускать.
6. **SSL GigaChat отключён намеренно** — при правках вокруг `gigachat_client.py` не «чинить».
7. **Классификация LLM недетерминирована:** даже с усиленным промптом (B1.3) возможен редкий offtopic на «устал» — детерминированный маршрут по флагу `awaiting_mood` (B1.2) является основной защитой, промпт — второй линией.

## Допущения

1. **Корень бага 1** — LLM-классификатор (`classify_with_llm` через `parameter_extraction_prompt.txt:11` «либо сомнение — offtopic») возвращает `offtopic` на голое «устал»: детерминированный `precheck_message` такое сообщение не блокирует (`guardrails.py:51-61`), а `mood_triggers` с «устал» (`dialogue_manager.py:1056`) находится в `_handle_general_request`, до которого при `offtopic` не доходит. Логи от 25.09 недоступны — вывод по анализу кода.
2. **Флаг `awaiting_mood`** хранится в JSON `dialogue_sessions.last_params` (ключ напр. `_awaiting_mood`) — без изменения схемы БД; если implementer выберет отдельную колонку — синхронизация `database.py`+`init_db.py` обязательна.
3. **Баг 3** трактается как отсутствие быстрого входа в УЖЕ реализованный watchlist (B4 старого бэклога ✅) с экрана `/start`, а не как отсутствие самой функции.
4. **Баг 2** — способ исправления (send+delete служебного сообщения vs полное удаление `ReplyKeyboardRemove`) окончательно выбирает implementer в рамках критериев приёмки «ровно одно видимое сообщение после /start»; рекомендуемый — send+delete.
5. **Имя файла** — по дате баг-репорта (25.09.2026), как указал оркестратор; создан 26.09.2026.
6. Оценок в часах достаточно для `/make-task`; задачи B1–B3 самодостаточны для передачи воркеру.
