# dialogue-session-state Specification

## Purpose

Определяет, как хранится состояние диалога пользователя (последние
рекомендации, параметры последнего поиска) и кэш результатов поиска,
чтобы контекст разговора не терялся при рестарте приложения, был
доступен при нескольких рабочих процессах и пользователи не влияли
на кэш друг друга.

## Requirements

### Requirement: Сохранение сессии диалога после рестарта

Система ДОЛЖНА (MUST) сохранять сессию диалога пользователя (последние
выданные рекомендации и параметры последнего поиска) в постоянном
хранилище, доступном после перезапуска процесса приложения.

#### Scenario: Контекст сохраняется после рестарта сервиса

- **WHEN** пользователь получил список рекомендаций, затем сервис
  перезапущен, и пользователь просит «похожие фильмы»
- **THEN** система возвращает похожие фильмы на основе предыдущей
  выдачи, а не просит начать поиск заново

### Requirement: Общая сессия для нескольких рабочих процессов

Система ДОЛЖНА (MUST) обеспечивать доступность сессии диалога
пользователя независимо от того, какой рабочий процесс обработал запрос.

#### Scenario: Последовательные запросы обрабатывают разными воркеры

- **WHEN** пользователь получил рекомендации в запросе, обработанном
  одним рабочим процессом, и затем отправляет уточняющий запрос,
  обработанный другим рабочим процессом
- **THEN** уточняющий запрос видит контекст предыдущего (последние
  фильмы и параметры поиска)

### Requirement: Изоляция кэша поиска между пользователями

Очистка кэша результатов поиска и признаки ошибок поиска ДОЛЖНЫ (MUST)
быть изолированы по пользователям: действия или ошибки одного
пользователя НЕ ДОЛЖНЫ (MUST NOT) очищать или инвалидировать
кэшированные результаты других пользователей.

#### Scenario: Запрос «похожие» одного пользователя не затрагивает других

- **WHEN** пользователь А запрашивает «похожие фильмы», что требует
  обновления результатов поиска
- **THEN** кэшированные результаты поиска пользователя Б остаются
  доступными и используются без повторного обращения к внешнему API

### Requirement: Истечение неактивных сессий

Система ДОЛЖНА (MUST) удалять сессии диалога, неактивные дольше
заданного времени (по умолчанию 1 час). Удаление ДОЛЖНО (MUST)
фактически выполняться в процессе работы сервиса, а не только быть
объявленным.

#### Scenario: Просроченная сессия очищается

- **WHEN** с момента последней активности пользователя прошло больше
  1 часа и пользователь отправляет новый запрос
- **THEN** система обрабатывает запрос с чистым контекстом (без
  прежних рекомендаций и параметров)

#### Scenario: Активная сессия не удаляется

- **WHEN** пользователь обращался к сервису в пределах последнего часа
- **THEN** его сессия с контекстом сохраняется

### Requirement: Неблокирующие операции с хранилищем сессий

Чтение и сохранение сессии диалога НЕ ДОЛЖНЫ (MUST NOT) блокировать
асинхронный цикл обработки сообщений: обращения к хранилищу сессий
ДОЛЖНЫ (MUST) выполняться вне цикла событий (в отдельном потоке или
через асинхронный драйвер). Чтение сессии НЕ ДОЛЖНО (MUST NOT)
выполнять запись в хранилище «только ради чтения».

#### Scenario: Медленное хранилище не останавливает бота

- **WHEN** хранилище сессий отвечает с задержкой и бот одновременно
  обрабатывает сообщения нескольких пользователей
- **THEN** задержка сохранения/чтения сессии одного пользователя
  не приостанавливает приём и обработку сообщений остальных

#### Scenario: Чтение сессии не пишет в хранилище

- **WHEN** система читает сессию пользователя при начале обработки
  сообщения
- **THEN** операция чтения не выполняет фиксацию транзакции
  и не изменяет данные сессии в хранилище
