## Локализация багов (результаты исследования кода)

### Баг 1 — текст «🎭 Подобрать по настроению» не влезает
- `src/telegram_bot.py:280-290` (`build_onboarding_keyboard`, :267): первый ряд — ДВЕ inline-кнопки: `RANDOM_MOVIE_BUTTON_TEXT = '🎲 Случайный фильм вечера'` (:137, 26 симв.) и `MOOD_BUTTON_TEXT = '🎭 Подобрать по настроению'` (:138, 26 симв.).
- Тип клавиатуры — **inline** (`InlineKeyboardMarkup`). Лимит Bot API 64 символа НЕ нарушен (`truncate_button_text`, `dialogue_manager.py:261`); «не влезает» = две кнопки в одном ряду делят ширину экрана (~по 50%), Telegram обрезает подпись многоточием.
- Перенос `\n` в inline-кнопках работает (высота кнопки растёт автоматически) — применим; надёжнее — вынести длинную кнопку в отдельный ряд на всю ширину (образец: ряд «📌 Мой список» :291-296, добавлен B3).

### Баг 2 — не работают «Не моё» / «Смотрел» / «Статистика» / кнопки оценок (КРИТИЧЕСКИЙ)
- Хендлеры в коде ЕСТЬ и зарегистрированы: единый `CallbackQueryHandler(handle_movie_detail)` (`telegram_bot.py:2184`) → таблица `_CALLBACK_ROUTES` (:2056-2084): префикс `fb:` (`FEEDBACK_CALLBACK_PREFIX`) → `_handle_feedback_callback` (:1981-2014) → `_record_feedback` (:1920-1978) для `fb:watched:{id}` / `fb:nope:{id}` / `fb:score:{id}:{n}` / `fb:clear:{id}`; «📊 Статистика» — `STATS_CALLBACK = 'menu:stats'` (:239, :567) → `_handle_menu_callback` (:1518, ветка 'stats' :1536/:1552-1565, адаптер `_as_message_update` :1505) → `handle_stats_command` (:2019-2048).
- Кнопки шлются С callback_data (`dialogue_manager.py:646-648, 668, 675` — `build_feedback_row`/панель оценки); префиксных коллизий в `_CALLBACK_ROUTES` нет.
- **Общий знаменатель «сломавшихся» кнопок — зависимость от PostgreSQL-таблиц** `movie_feedback`, `watchlist`, `user_statistics`: запись реакций/оценок (`feedback_manager.py:77-152`, `_upsert`) и чтение сводки (`stats_manager.py:100-140`, ОДИН контекст на три таблицы — отсутствие ЛЮБОЙ из них роняет всю сводку → `available=False`). Остальные кнопки (random/mood/top/similar/info) от БД не зависят и в отчёте не фигурируют.
- **Корень (основная гипотеза, подтверждается кодом деплоя)**: схема новых таблиц создаётся ТОЛЬКО ручным `python init_db.py` (`init_db.py:39`, `db.create_all()`); `Dockerfile` CMD = `python src/telegram_bot.py` — create_all при старте бота НЕ выполняется; `.github/workflows/deploy.yml` шаг init_db НЕ запускает. Пользователь воспринимает это как «кнопки не работают».

## Риски и ограничения

1. **Доступ к VPS**: T2/T8 требуют SSH на прод (38.180.228.133) и деплой тегом — пайплайн autodev этого НЕ может; задачи выполняются человеком-оператором по инструкции, ✅ ставит оркестратор только после фактической проверки. Без T2 гипотеза корня бага 2 остаётся неподтверждённой (код деплоя strongly указывает на неё, но локальных логов теста 04.10 нет).
2. **Нет dry-run Telegram** (AGENTS.md): проверка бота — только импорт-чек, unit-тесты с моками PTB и (для T2) ручной прогон на проде; polling локально НЕ запускать.
3. **Дубли моделей БД** (`src/models/database.py` + `init_db.py`): T1/T8 НЕ должны создавать третий источник схемы — только `db.create_all()` поверх существующих моделей; при любом изменении схемы синхронизировать оба места.
4. **In-memory сессии и кэш** (`session_manager.py`, `MovieAgent._search_cache` TTL 45 с): флаги `_awaiting_mood`/снапшоты страниц теряются при рестарте — кнопки T5/T6 спроектированы так, чтобы НЕ зависеть от in-memory состояния (детерминированный prefilter / прямой запрос).
5. **Промпты как источник поведения** (`src/prompts/*.txt`): тексты запросов кнопок T6 («посоветуй лучшие фильмы в жанре X») должны уверенно классифицироваться существующим intent-промптом; менять промпты в рамках задач НЕ планируется, но проверить классификацию моками обязательно.
6. **CURRENT_YEAR в 3+ местах** (ловушка AGENTS.md): новые клавиатуры год не используют; в T5/T6 не добавлять четвёртый хардкод (образец дисциплины — `_TOP_QUERY_BY_SEGMENT`).
7. **SSL GigaChat отключён намеренно** — не трогать при любых правках клиентов.
8. **Консоль cp1251**: локальные прогоны скриптов с эмодзи-логами — только с `PYTHONIOENCODING=utf-8`; запуск бота `python src\telegram_bot.py` (НЕ `-m`, плоские импорты `src/`).
9. **Лимит callback_data 64 байта**: русские подписи/ключи в `mood:pick:`/`genre:pick:` — короткие ключи словаря, не полные тексты; guard-тест T7 фиксирует инвариант.
10. **Порядок выполнения**: все P0 (T1→T2, T3 независимо) → верификация (ruff/mypy/pytest + T4) → P1 → P2; T2 блокируется деплоем и может выполняться параллельно с T4-T7.
11. **Сохранность прод-данных (T11–T14)**: прод-БД `kinobot_db` (volume `postgres_data` контейнера `kinobot_postgres`) содержит боевые данные — ЛЮБОЕ изменение схемы только через миграции additive-first; `drop_table`/`drop_column`/`downgrade` на проде запрещены; перед накатом миграций в деплое — pg_dump-бэкап с ротацией (T12). Существующая прод-БД вводится в управление миграций через `alembic stamp head` (без DDL), а НЕ через upgrade.
12. **Autogenerate-ловушки Alembic**: автогенерация не отражает server_default, различия типов и порядок индексов — каждую миграцию вычитывать вручную; guard-тест «модели == миграции» (T13) ловит только структурный рассинхрон, не семантический.
13. **Гонка контейнеров при миграциях**: миграции накатывает ОДИН процесс (бот, `RUN_MIGRATIONS`/стартап-хук T12); одновременный `upgrade head` из kinobot и kinobot-web на Postgres защищён транзакционностью DDL, но дублирующий лог/ожидание блокировки нежелательны — зафиксировать единственного раннера.
14. **Откат релиза не откатывает схему**: `workflow_dispatch` на старый тег оставит схему новой — совместимость «старый код + новая схема» обеспечивается additive-first (старый код игнорирует новые колонки); downgrade схемы на проде — только вручную с бэкапом.
