## Context

Рабочая копия находится в середине незавершённого рефакторинга: импорты
переведены с пакетных на плоские, но не полностью (см. proposal.md — Why).
Продакшен работает на образе 1.0.3 из прежнего кода; деплой — ручная
сборка → реестр cloud.ru → VM (состав сервисов на VM до конца не ясен,
см. «Открытые вопросы»). Ограничения: только один внешний инфраструктурный
компонент помимо приложения — PostgreSQL (уже используется), никакого
оркестратора и управляемого кэша на VM нет.

## Goals / Non-Goals

**Goals:**

- Вернуть запуск бота и веба из текущей рабочей копии (локально и в
  Docker-образе).
- Сделать состояние диалога переживающим рестарт и общим для воркеров,
  не добавляя новых сервисов в инфраструктуру.
- Убрать глобальное взаимовлияние пользователей через кэш.
- Задать базовую инженерную гигиену: тесты, статический анализ,
  единые источники правды (модели БД, текущий год, конфиг).

**Non-Goals:**

- Не менять алгоритмы рекомендаций и поведение промптов (кроме удаления
  из промпта необработанных интентов `newer`/`older`, если решено их не
  реализовывать).
- Не переводить инфраструктуру на Redis/Kubernetes и не менять схему
  деплоя (реестр + VM остаются).
- Не реализовывать полноценный вебхук-режим в этом изменении.

## Decisions

### 1. Модель импортов: плоские, CMD контейнера без `-m`

Оставляем плоские импорты в `src/` (переход уже выполнен в рабочей копии
почти во всех модулях; `app.py` исторически рассчитывает на них через
`chdir`/`sys.path`). CMD в `Dockerfile` меняется с
`python -m src.telegram_bot` на `python src/telegram_bot.py`
(WORKDIR `/app`).
Альтернатива: откатить импорты к пакетным и оставить `-m` — отвергнута:
пришлось бы переделывать те же файлы обратно, плюс `app.py` всё равно
использует плоскую схему, и два стиля снова разошлись бы.
Команда запуска и запрет `-m` фиксируются в документации.

### 2. Исправление `recommendation_engine.py:271`

Относительный импорт `from .utils.movie_filter import is_russian_content`
заменяется использованием уже существующего плоского импорта из начала
файла (`is_russian_content` добавляется в тот же импорт). Никакой второй
точки импорта не нужно.

### 3. Хранилище сессий диалога: PostgreSQL, без новых сервисов

Сессии (`last_movies`, `last_params`, метаданные) переносятся в таблицу
PostgreSQL (создаётся через `create_all`, декларативно вместе с
остальными моделями в `src/models/database.py`). Чтение/запись — при
начале и конце обработки запроса; внутри запроса работает копия в памяти.
Альтернативы:
- Redis — удобнее (TTL из коробки), но это новый сервис на VM, которого
  там сейчас нет; откладываем до роста нагрузки.
- Оставить in-memory — не удовлетворяет требованиям спецификации
  `dialogue-session-state`.
Кэш поиска (`CACHE_TTL` 45 с) остаётся в памяти процесса — это
оптимизация, а не состояние: он НЕ обязан переживать рестарт, но обязан
стать изолированным по пользователям (ключ кэша дополняется `user_id`,
глобальный флаг `_last_search_failed` убирается/приватизируется).

### 4. Режим `BOT_MODE=webhook`: удалить

Текущая реализация не обрабатывает очередь обновлений (нет
`run_webhook`/запущенного апдейтера) и не проверялась. Продакшен
использует polling. Удаляем: ветку `BOT_MODE` в `app.py`,
`/telegram-webhook`, `setup_webhook`. `create_telegram_app` остаётся
как единственная точка сборки приложения бота (убирает дублирование
регистрации хендлеров с `main()`).
Альтернатива: реализовать через `run_webhook` — требует публичного HTTPS
и усложняет деплой без текущей потребности.

### 5. Ретраи: только временные ошибки

В `gigachat_client.py` и `kinopoisk_client.py` ретраятся только сетевые
ошибки и HTTP 429/5xx (уже есть неиспользуемые предикаты
`is_transient_error`/`is_kinopoisk_transient_error` — задействовать их).
Ошибки авторизации (401/403) не ретраятся, а логируются и приводят к
фолбэку (для LLM — следующая модель в `LLMRouter`).

### 6. `monitoring.py`: удалить

Модуль сломан (обращение к несуществующему `app`), зависимость
`prometheus_client` отсутствует, в деплое Prometheus нет. Если метрики
понадобятся — отдельное изменение с фабрикой приложения.

### 7. Единая инициализация БД

Единственная точка входа — `init_db.py`, который импортирует модели из
`src/models/database.py` (определения моделей из самого `init_db.py`
удаляются). Flask-команда `init_db` из `app.py` удаляется. `init_db.py`
не должен тянуть `app.py` с его побочными эффектами.

### 8. Текущий год — один источник

`config.py` вычисляет `CURRENT_YEAR = datetime.date.today().year`;
все хардкоды (`telegram_bot.py`, `dialogue_manager.py`,
`movie_agent.py`, `movie_filter.py`) заменяются на него. Примеры годов
в промпте — иллюстративные и замене не подлежат.

### 9. Логирование

`setup_logging` настраивает файловый хендлер корневого логгера один раз
(идемпотентно, без повторных `addHandler`) и возвращает именованный
логгер сервиса. Каталог логов задаётся переменной окружения `LOG_DIR`
(по умолчанию `logs`, разрешается в абсолютный путь на момент старта).
Сохраняется документированная особенность: веб пишет в `src/logs/`
из-за `chdir` в `app.py` — это поведение не меняется, чтобы не ломать
том `app_logs` в деплое.

### 10. Зависимости и CI

Из `requirements.txt` удаляются неиспользуемые `pandas`, `numpy`,
`requests`; дубль `gunicorn` убирается. Тестовые/dev-зависимости
(`pytest`, `ruff`, `mypy`) — в отдельном `requirements-dev.txt`.
У репозитория есть удалённый репозиторий на GitHub — CI реализуется
как GitHub Actions: ruff + mypy + pytest + сборка образа.

### 11. Безопасность админки

- `init_db.py`: без `ADMIN_PASSWORD` в окружении — ошибка и выход;
  пароль не печатается.
- `app.py`: `FLASK_SECRET_KEY` обязателен при `FLASK_ENV=production`
  (fail-fast); в разработке допустим временный ключ с предупреждением
  в логе. `debug=True` — только при явном режиме разработки.
- Дефолтные значения `admin123` и захардкоженный секрет удаляются.

## Risks / Trade-offs

- [Смена CMD и импортов может сломать сборку образа] → после правок
  собрать образ локально, поднять контейнер и проверить старт бота
  до пуша в реестр.
- [Сессии в PostgreSQL добавляют зависимость диалога от БД] → при
  ошибке чтения/записи сессии прозрачный фолбэк на in-memory сессию
  с предупреждением в лог; диалог не падает.
- [Удаление вебхук-заготовок] → убедиться, что на VM нет сервиса,
  рассчитывающего на `/telegram-webhook` (см. «Открытые вопросы»).
- [Ретраи только временных ошибок ускорит проявление неверных ключей] →
  это ожидаемо: ошибки авторизации должны быть видны сразу в логах.
- [Перенос сессий в БД требует новой таблицы] → таблица создаётся через
  `create_all` без изменения существующих; операция не деструктивная.

## Migration Plan

1. Закоммитить незакоммиченную работу над админкой отдельным коммитом
   (до любых правок) — точка безопасного отката в git.
2. Выполнить фазу 0; локальная проверка: запуск бота из корня,
   `GET /health` веба, сборка образа и старт контейнера.
3. Выполнить фазы 1–3; после каждой — локальная проверка запуска.
4. Перед деплоем фазы 3 убедиться, что в окружении на VM заданы
   `ADMIN_PASSWORD` и `FLASK_SECRET_KEY`.
5. Поднять тег образа (например, 1.1.0), обновить `docker-compose.yml`,
   задеплоить на VM по процедуре из `docs/`.
6. Откат: вернуть тег 1.0.3 в compose-файле на VM и перезапустить —
   образ остаётся в реестре.

## Open Questions

- Какие сервисы реально запущены на VM (`docker-compose.prod.yml` вне
  репо): только бот или бот + веб/админка? Уточнить перед деплоем фазы 3.
- Интенты `newer`/`older`: удалить из промпта или реализовать — решить
  при актуализации документации, на спецификации это не влияет.
- Понадобится ли хранить полную историю диалога (сейчас в сессии только
  последняя выдача и параметры) — решится по мере развития продукта.
