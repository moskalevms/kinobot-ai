- **Дата**: 2026-10-04
- **Источник**: пользовательский ввод — диагностика по фактам из логов
  `backlog/state/logs/` (кейсы T2, T4 от 2026-10-04), state-файла

  живых воркеров (heartbeat, wall-time лимит, watchdog-скрипт); P1 —

  пайплайна — markdown (`.opencode/skills/autodev-pipeline/SKILL.md`,
  `.opencode/agent/*.md`) + вспомогательные PowerShell-скрипты
  (`.opencode/scripts/`). Верификация = ручной тест скриптов И/или контрольный
  прогон пайплайна на учебной задаче (см. «Допущения»).

    - Скрипт `Wait-Worker.ps1 -TaskId <ID> -Pid <PID> -Heartbeat <путь>
      -StaleMin 10 -BudgetMin 90 -Verdict <путь>`:
      - при спавне фиксирует `deadline_at = now + BudgetMin` (пишет в state и

      - цикл раз в 20–30 с: (а) **heartbeat устарел > `StaleMin` (10 мин)** →

        оставить сирот.
      - Результат пишет в `backlog/state/verdict-<ID>.json`:
        `{status: exited|killed-hang|killed-walltime, pid, started_at,

      implementer/verifier длятся десятки минут — кейс T4: 30 мин без
      обновления state у здорового воркера); источник истины о зависании —
      heartbeat + wall-time из `Wait-Worker.ps1`.
    - Перезапуск единицы после kill — штатно: `attempt+1`, ≤3 (уже есть в
      SKILL.md «Отказоустойчивость»), бюджет исправлений не тратится.
  - Критерий приёмки:
    - Ручной тест (имитация): запущен «подставной» долгий процесс
      (например `Start-Sleep 3600` через обёртку с heartbeat); при
      `-StaleMin 1 -BudgetMin 2` watchdog убивает его по обоим сценариям
      (остановка heartbeat; наступление deadline), verdict-файл создаётся с
      корректным `status` и `tail_err`, дочерних процессов-сирот не осталось
      (проверка `Get-CimInstance Win32_Process`).
    - `worker.deadline_at` присутствует в схеме state в SKILL.md.
    - Контрольный прогон учебной задачи: воркер, отработавший штатно, даёт
      verdict `exited`; диспетчер принимает решение по verdict-файлу.

## Риски и ограничения

1. **Инвалидация префиксного кэша (AGENTS.md «Контекст и токены»)**: правки
   SKILL.md/`.opencode/agent/*.md` в активной серии сессий сбрасывают кэш и
   жгут токены. Применять изменения этого бэклога строго **между прогонками
   пайплайна** (не во время живого `/make-task`), ideally одним батчем P0.
2. **Heartbeat-обёртка живёт отдельно от воркера**: обёртка может продолжать
   писать heartbeat, пока сам `opencode run` завис на LLM-стриме (провайдер
   bailian/qwen, сетевые таймауты). Митигируется жёстким wall-time
   `deadline_at` (W2) — kill независимо от «свежести» heartbeat.
3. **Сироты при убийстве**: `opencode.cmd` → node → дочерние процессы;
   `Stop-Process` по одному PID оставляет сирот, которые продолжают жечь
   токены/порты. Обязательный kill деревом (`taskkill /T /F`) в W2 +
   проверка сирот в критериях приёмки.
4. **Переиспользование PID** до внедрения W6 остаётся источником ложных
   «жив» — порядок выполнения: W1→W2→W3 раньше W6 не откладывать надолго.
5. **Кодировка может не поддаваться chcp**: node/opencode может писать в
   OEM-кодировку независимо от `chcp 65001` в обёртке; в W4 заложен fallback
   (чтение в OEM-кодировке). Риск — acceptance W4 достигается только
   fallback-вариантом.
6. **Контрольные прогоны стоят реальных токенов и времени** (LLM-вызовы,
   учебная задача проходит полный цикл implementer/verifier/reviewer).
   Планировать их между сессиями, закладывать бюджет.
7. **Scope-guard может дать ложные blocked**: задача, легитимно требующая
   сети (webfetch документации, api.kinopoisk.dev в тестах), не должна
   попадать под запрет — в W7 запрещены именно SSH/прод/долгие вызовы,
   белый список фиксируется явно.
8. **Watchdog убивает здоровый, но медленный воркер**: wall-time 90 мин может
   не хватить группе задач с 3 итерациями исправлений и 900+ тестами.
   Митигируется W11 (настраиваемый бюджет) и тем, что kill → attempt+1
   идемпотентно продолжает работу по артефактам, а не теряет её.
9. **State-файл — точка конкуренции**: heartbeat-монитор и watchdog не должны
   писать `autodev-state.json` одновременно с воркером (риск порчи JSON).
   Heartbeat — только отдельный файл (W1); watchdog пишет state только после
   смерти воркера (W2); verdict — отдельный `verdict-<ID>.json`.

## Допущения

1. Числовые дефолты выбраны разумно и настраиваемы: heartbeat-период 3 мин,
   порог устаревания `StaleMin` 10 мин, wall-time на задачу 90 мин,
   перезапуски attempt ≤3 (уже в SKILL.md).
2. Скрипты размещаются в `.opencode/scripts/` (версионируются git), а НЕ в
   `backlog/state/scripts/` — т.к. `backlog/state/` в .gitignore (локальный
   рантайм); runtime-артефакты (heartbeat, verdict, hang-отчёты) остаются в
   `backlog/state/`.
3. Учебная задача для контрольных прогонов: одна незакрытая `- [ ]` задача из
   `backlog/backlog_2026-10-04_bugfix_telegram_ui.md` (например T5) или
   специально добавленная тривиальная задача `W-test`; если T5 к моменту
   выполнения уже закрыта — взять любую малую задачу из P1 текущего бэклога
   багфиксов.
4. Верификация markdown-задач (W3, W5-док, W7, W8, W9) = grep-проверка
   текстов + контрольный прогон пайплайна; pytest/ruff/mypy к самим
   `.opencode/**` файлам неприменимы (это не Python-код kinobot-ai), но
   контрольный прогон обязательно включает зелёный verifier по коду учебной
   задачи.
5. ID `W*` не пересекаются с `T*`/`A*`/`B*`/`C*` существующих бэклогов;
   отметки `- [x]`/`✅` проставляет оркестратор пайплайна после реализации и
   верификации соответствующей задачи.
6. Изменения не требуют правок AGENTS.md (все потоки описаны в SKILL.md и
   агентах); если по итогам P0 понадобится поправка AGENTS.md — отдельной
   задачей между прогонками.
